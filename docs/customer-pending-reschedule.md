# Customer self-service pending reschedules

Customers signed in through the original LINE account see pending hours in Book and My Bookings. Each original booking has its own Choose new time button. They select a duration and an eligible available time on the original court. A partial assignment preserves a separate pending remainder. The total original money, discounts and package minutes across the two records are preserved; no payment or Pass deduction is performed again.

First release supports paid court bookings and Ultra Starter / Ultra Pass court entitlements. Coach lessons, Off-Peak, Event Passes, refunded/restored entitlements and unpaid/review bookings show a contact-admin explanation. A receipt already issued for a booking permits full assignment only; an admin must manage the receipt before splitting. Pass targets must be within the active original package's validity. Cash targets cannot exceed the proportional original price before coupon discount; a cheaper target does not create a refund. Customers cannot change court, transfer hours to another LINE account or combine multiple bookings into one.

The existing `/api/booking` endpoint exposes `pending_reschedules`, `pending_reschedule_options` and `assign_pending_reschedule`. All require a verified Firebase ID token; ownership is checked by its UID, never by customer-supplied name, phone or LINE ID. Availability and policy are checked again inside the shared admin/customer assignment transaction. A stale source booking is rejected, including concurrent admin/customer assignments. A pending source owns no former slots and cannot overwrite a later booking occupying them. Source records marked as tests and test-only availability are excluded.

The transaction writes the booking, any remainder, public slots and private claims atomically. Existing finance snapshots and receipt locks are retained. Assignment is audited as a customer action. Best-effort Calendar sync and LINE notifications run server-side after commit; Calendar failure uses the existing admin retry UI. A customer gets a successful booking even when a notification provider fails. After an ambiguous network failure, the UI requires reloading entitlements rather than blindly retrying.

Also fixes the admin Move to Pending button remaining disabled after its first success. Opening another booking and finishing any request restore the button; a customer may have multiple independently pending bookings.

Validation: Firebase Emulator integration tests cover ownership/auth, full and partial assignment, accounting conservation, receipt locks, Pass expiry and unchanged balance, eligibility, price bands, conflicts in former slots, duplicate submission and customer/admin races. Browser preview uses a separate local emulator project with external notification credentials cleared. No production bookings are created for verification.
